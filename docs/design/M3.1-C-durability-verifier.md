# LYR M3.1-C Design — Durability Verifier

**Status:** Proposed
**Stage:** M3.1-C
**Prerequisite:** [M3.1-C0 — verification task (frozen)](./M3.1-C0-durability-verification-task.md) · [durability-v1 benchmark](../../experiments/evaluation/benchmark/durability-v1/)

---

## 1. Purpose

Implement the task frozen in M3.1-C0: a **Durability Verifier** that decides whether
a proposed durable memory deserves long-term persistence, and vetoes the ones that
don't. First version only — **no challenger, no multi-round reasoning, no statement
rewriting.** One component, one question.

The concrete target (M3.1-C0 eval map): on `durability-v1`, drive **false positives on
the 5 `no` cases down** (coffee, donuts, cloud-growth, rent, version-bumps) **without
creating false negatives on the 13 `yes` cases** (acquisition, guidance reversal,
family preference, API sunset, …).

---

## 2. Architecture (minimal)

```
Judgment Unit
   ↓
JudgmentBuilder      ── proposes a durable memory (does not commit yet)
   ↓  proposed intent
DurabilityVerifier   ── KEEP | REJECT | UNSURE   (the one question)
   ↓  verdict
Engine commit        ── KEEP/UNSURE → write ;  REJECT → NO_OP
   ↓
JudgmentRecord       ── now carries the verdict as decision provenance
```

**Where the verifier plugs in.** It is a separate, injectable, **stateless**
component — but it gates at the builder's commit boundary, so `update()` becomes
*propose → verify → commit* internally. This realizes C0 §1 exactly ("the engine
commits `NO_OP` **instead of** the write") with no commit-then-retire churn, and keeps
`JudgmentBuilder.update(...)`'s **signature unchanged** — the verifier is injected at
construction, defaulting to `None` (→ today's behavior). Same injection pattern as
`store` / `extractor` / `consolidator`.

> Rejected alternative: commit first, then retire on REJECT. It works via the existing
> tombstone lifecycle but creates a v1-then-retired churn for every rejected memory.
> Gating before commit is cleaner and matches C0's wording.

---

## 3. The verifier interface

```python
class DurabilityVerifier(Protocol):
    def verify(self, proposal: ModelProposal, evidence: list[Node]) -> Verdict: ...
```

- **`proposal`** — the builder's proposed durable (statement, kind, rationale,
  confidence, evidence ids). From the `JudgmentRecord`.
- **`evidence`** — the semantic nodes the proposal cites: *the Builder's judgment
  context* (C0 §2), no more. **Not** candidate durables, **not** source records.
- **Stateless** (C0 §5): `verify` sees exactly one proposal and its evidence — no
  history, no other pending judgments.

Two implementations:
- **`LLMDurabilityVerifier(client)`** — asks the model the one question (§6).
- **`ThresholdDurabilityVerifier`** — a deterministic baseline/control (e.g. KEEP iff
  builder-confidence ≥ t), so the pipeline is testable offline and the LLM verifier
  has something to beat. Not a real durability policy — a control, like
  `RecurrenceConsolidator` was.

---

## 4. Inputs (frozen, = C0 §2)

The verifier receives **only**: the proposed `ModelProposal` + the cited semantic
`Node`s. It never reads candidate durables or source records.

---

## 5. Outputs & engine mapping (frozen, = C0 §4)

`Verdict = KEEP | REJECT | UNSURE` (+ `rationale`, `confidence`).

| Verdict | Engine action | Durable committed? | Notes |
|---|---|---|---|
| **KEEP** | the proposed `ADD`/`UPDATE`/`MERGE` | yes | normal |
| **REJECT** | `NO_OP` | no | `rejection_reason = "verifier: REJECT — <why>"` |
| **UNSURE** | the proposed write | yes, **flagged** | node `attributes["verification"] = "unsure"`; retention-biased (C0 §4) |

UNSURE is verification confidence, **not** a third durability class (C0 §4) — the
committed node is an ordinary durable that happens to carry an `unsure` flag.

---

## 6. The verifier prompt (`durability_verifier_v1`)

One canonical, versioned file (like the builder/decomposer prompts). It asks exactly
the C0 §3 question and nothing else:

```
You decide whether a proposed long-term ("durable") memory is worth keeping.
Answer ONLY: should this become long-term knowledge?

A durable memory is worth keeping if it is a lasting lesson, decision, stable
preference, persistent pattern, or significant fact. It is NOT worth keeping if it is
a trivial or routine observation, however often it recurs (a coffee habit, donuts at a
standup, a single ordinary metric, a routine expense, a version bump).

Proposed durable memory:
  statement: <…>
  kind: <…>
Evidence it is based on:
  <cited semantic records>

Return ONLY JSON:
  {"verdict": "KEEP" | "REJECT" | "UNSURE", "confidence": 0.0, "reason": "…"}

REJECT trivia. KEEP genuine long-term knowledge. Use UNSURE only for genuine
borderlines — it is retained, not dropped.
```

No grounding check, no scope check, no contradiction check — those are separate
stages with their own task definitions (C0 scope boundary).

---

## 7. How the verdict is recorded

A new **frozen** field on `JudgmentRecord`:

```python
@dataclass(frozen=True)
class Verdict:
    verdict: str            # KEEP | REJECT | UNSURE
    rationale: str = ""
    confidence: float | None = None
    model_config: dict = …  # provider / model / prompt_version (verifier's own)

# JudgmentRecord gains:  verification: Verdict | None = None   (None = not verified)
```

So a record now tells the whole story: **what the model proposed** (`model_intent`),
**whether it should persist** (`verification`), and **what the engine did**
(`final_engine_action`). Back-compatible: existing records/tests have
`verification = None`.

---

## 8. Execution order (frozen)

```
decompose → for each unit:
    builder proposes  (prompt → parse → ModelProposal)
    verifier.verify(proposal, evidence)  → Verdict
    engine commits     (KEEP/UNSURE → write ; REJECT → NO_OP)
    JudgmentRecord written (model_intent + verification + final_engine_action)
```

The verifier runs **once per proposed durable**, after the builder, before commit.

---

## 9. First cases that must pass (from `durability-v1`)

| case | required verdict |
|---|---|
| coffee ritual · donuts · routine rent · version bumps | **REJECT** |
| cloud-growth 31% (single quarter) | REJECT *(pending human label confirm)* |
| acquisition · guidance reversal · family preference · API sunset · CI flakiness · dividend policy · gRPC migration · auth-fragility · letters | **KEEP** |

The rent and version-bump cases were already `NO_OP` from the builder — the verifier
must not *un*-reject them; the live wins are coffee/donuts/cloud-growth.

---

## 10. Benchmark metric (frozen)

Scored on `durability-v1` per C0's map. The **single number M3.1-C must move**:

```
false positives on the 5 `no` cases → 0   (currently 3: coffee, donuts, cloud-growth)
subject to: false negatives on the 13 `yes` cases = 0   (hard constraint)
```

`borderline` (SRE hire) and any `UNSURE` verdicts are excluded from strict scoring.

---

## 11. Non-goals (v1)

No challenger, no multi-round/debate, no statement rewriting, no re-operation
(`ADD→UPDATE`), no cross-judgment/global reasoning, no grounding/scope/contradiction
checks, no benchmark expansion. All deferred.

---

## 12. Implementation plan

- **M3.1-C** — `DurabilityVerifier` protocol + `LLMDurabilityVerifier` +
  `ThresholdDurabilityVerifier`; `Verdict` + `JudgmentRecord.verification`; verifier
  injection into `JudgmentBuilder` (propose→verify→commit); canonical prompt; harness
  `--verify`. Tests via `FakeClient`. Builder `update()` signature unchanged.
- **M3.1-C.1** — run the LLM verifier live over `durability-v1`, score against the
  labels, report false positives / negatives. Only then consider expanding the
  benchmark.

---

## 13. Exit criteria

- coffee / donuts / cloud-growth → REJECT; the 13 `yes` cases → KEEP (no false negatives)
- every committed durable version carries a `verification` verdict
- `JudgmentBuilder.update()` signature unchanged; existing tests unaffected
- verifier is stateless and reads only proposal + cited evidence
- one number reported on `durability-v1`: false positives on the `no` cases
