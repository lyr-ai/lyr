# LYR M3.1-B.2 Design — Judgment Decomposition

**Status:** Proposed
**Stage:** M3.1-B.2
**Prerequisite:** [M3.1-E — Cross-Domain Judgment Validation](./M3.1-E-cross-domain-judgment-validation.md)

---

## 1. Motivation

M3.1-E evaluated the minimal Durable Builder across four domains (memoir, meeting
notes, financial report, git history) with the same Builder and prompt. The result
was consistent: the dominant failure was **F7 — Candidate Coverage Failure**, in
all four domains.

It was **not** a model-reasoning failure. Across all four the model produced
grounded judgments, correctly identified duplicate evidence, scoped most
conclusions, and chose reasonable operations. The failure occurred earlier: each
input batch held multiple independent durable candidates, but the Builder produced
exactly one JudgmentRecord and silently discarded the rest.

This supports **Outcome B**: the Builder interface is insufficient for multi-topic
batches. This milestone investigates that limitation.

---

## 2. Research Question

Not *"how can the Builder generate multiple judgments?"* but:

> **How should semantic evidence be decomposed into independent judgment units?**

The experiment suggests one judgment remains a useful *atomic* reasoning unit, but
one *batch* is not necessarily one judgment. The problem is **judgment
decomposition**, not judgment quality.

---

## 3. Design Goals

- **G1. Preserve judgment atomicity.** One JudgmentRecord = one reasoning process =
  one maintenance operation. Unchanged.
- **G2. Separate decomposition from judgment.** The Builder does not decide how many
  topics exist; decomposition is an explicit stage *preceding* the Builder.
- **G3. Preserve the existing Builder API.** `JudgmentBuilder.update(semantic_nodes,
  candidate_durable_nodes) -> JudgmentResult` is unchanged; it still operates on one
  judgment at a time.
- **G4. Preserve audit simplicity.** Each JudgmentRecord stays independently
  understandable, reviewable, replayable, verifiable. No record holds multiple
  unrelated decisions.

---

## 4. Proposed Architecture

```text
Semantic Nodes → Judgment Decomposer → [Unit A, Unit B, Unit C]
                                            │        │        │
                                   update() update() update()   (Builder unchanged)
                                            │        │        │
                                        Record   Record   Record
```

The decomposition stage determines *how many* judgments exist; the Builder is
looped, unchanged, over the units.

---

## 5. Judgment Unit

The minimal semantic context required for one durable decision:

- semantic nodes (one coherent topic)
- candidate durable memories
- local evidence context

Illustrative decompositions: memoir → {family priorities, emigration, letters};
meeting → {billing-API sunset, CI flakiness, DB migration}; financial → {acquisition,
dividend policy, guidance revision, impairment}; git → {REST→gRPC, auth instability,
caching}.

---

## 6. Candidate Decomposition Strategies

The milestone does **not** prescribe one algorithm. Candidates:

- **A. Connected components** over semantic relationships.
- **B. Embedding clustering.**
- **C. LLM topic segmentation.**
- **D. Incremental extraction:** find the strongest durable candidate → remove its
  supporting evidence → repeat.

The goal is to find the abstraction that best fits the Builder; algorithm selection
is secondary. (Implementation note: LYR's fixtures are mostly flat `event` records
with no relationship edges, so **C** is the natural first working strategy;
deterministic **whole-batch** and **singleton** decomposers serve as the "before"
control and an over-decomposition floor.)

---

## 7. Evaluation

Reuse the four M3.1-E domains. Dimensions:

- **Coverage** — are all obvious durable candidates represented?
- **Isolation** — does each unit contain only one coherent topic?
- **Stability** — does repeated decomposition produce similar units?
- **Audit quality** — is provenance preserved; is each record independently understandable?
- **Builder compatibility** — does the *unchanged* Builder operate on every unit?

---

## 8. Success Criteria

- current Builder API unchanged
- one JudgmentRecord still represents one durable decision
- decomposition exposes multiple durable candidates in multi-topic inputs
- F7 substantially reduced
- no degradation in groundedness or audit quality
- the four domains show improved candidate coverage

---

## 9. Non-Goals

Verifier, challenger, confidence calibration, prompt optimization, retrieval
redesign, cognitive memory, long-term planning. The sole objective is the correct
boundary between semantic batches and atomic durable judgments.

---

## 10. Exit Criteria

Proceed to M3.1-C only if decomposition consistently produces coherent units, the
existing Builder performs well on them, F7 is no longer dominant, and remaining
failures are primarily judgment quality rather than interface design.

---

## 11. Next Milestone

```text
M3.1-C:  Judgment Unit → Builder (Proposer) → Verifier → JudgmentRecord → Engine Commit → Durable
```

The Verifier then evaluates **one complete judgment** rather than compensating for an
incomplete interface.
