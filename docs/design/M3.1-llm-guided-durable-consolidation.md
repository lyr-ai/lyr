# LYR M3.1 Design Document — Automated Durable Judgment

**Status:** Draft — *design only*. This milestone ships **no implementation and no
schema migration**. Its output is this document and the decisions it frames.

## Status

LYR v0.2.0 provides a trustworthy Durable Layer substrate:

* stable node identity
* version history
* provenance
* inspectable proposals
* deterministic recurrence baseline
* merge lifecycle
* identity-safe updates
* evaluation harness

The existing `RecurrenceConsolidator` is intentionally limited. It provides a deterministic structural baseline, but recurrence is neither necessary nor sufficient for durability.

M3.1 introduces an automated semantic consolidation process.

---

## Objective

Build an automated Durable consolidation pipeline that can:

1. propose long-term knowledge from Semantic records;
2. verify that the proposed statement is supported;
3. search for conflicting or limiting evidence;
4. revise the statement when necessary;
5. commit only the final, evidence-backed judgment;
6. preserve the complete history of how that judgment was formed.

The system must not require routine user review.

---

## Core Research Question

**Can an automated system maintain durable, evidence-backed judgments by proposing, challenging, revising, and versioning them over evolving semantic evidence?**

---

## Motivation

A single LLM call can generate plausible abstractions, but plausibility is insufficient for long-term knowledge.

A naive pipeline is:

```text
Semantic Records
        ↓
LLM Summary
        ↓
Durable Memory
```

This creates several risks:

* unsupported generalization;
* repeated noise promoted as durable;
* important one-off events ignored;
* conflicting evidence omitted;
* excessive version churn caused by paraphrasing;
* high-level errors compounded in later Cognitive abstraction.

M3.1 replaces single-pass abstraction with an automated judgment process.

---

## Design Principle

```text
Model proposes meaning.
Model challenges meaning.
Engine commits identity, history, and provenance.
```

The model owns semantic judgment.

The engine owns:

* identity
* versioning
* lifecycle
* provenance
* invariant enforcement
* final persistence

No model may directly create or mutate persistent identifiers.

---

## High-Level Pipeline

```text
Semantic Records
        ↓
Candidate Selection
        ↓
Durable Proposal
        ↓
Evidence Verification
        ↓
Counter-Evidence Search
        ↓
Revision
        ↓
Commit Decision
        ↓
Engine Apply
```

The expected operations remain:

```text
ADD
UPDATE
MERGE
NO_OP
```

The engine may downgrade or reinterpret a model proposal when required by system invariants.

Examples:

```text
ADD targeting an existing identity
→ UPDATE / evolve
```

```text
UPDATE with no material change
→ NO_OP
```

```text
MERGE involving an invalid or retired target
→ reject proposal
```

---

## Non-Goal

M3.1 does not guarantee truth.

It maintains:

> the current best automated, evidence-backed, revisable judgment.

A Durable node is therefore not an unquestionable fact. It is a versioned knowledge claim supported by semantic evidence and produced through a recorded judgment process.

---

## Durable Node

M3.1 continues using the existing unified `Node` model.

The engine-owned fields remain fixed:

```text
layer = durable
identity
version
evidence
status
history
provenance
```

Model-proposed content remains open:

```text
kind
statement
attributes
candidate identity match
```

`kind` must not become a required enum.

Examples may include:

* lesson
* decision
* preference
* pattern
* constraint
* interpretation
* principle
* state
* relationship

These values are descriptive metadata, not schema-enforced ontology.

---

## Judgment Record

Every automated consolidation attempt must produce a persisted `JudgmentRecord`.

A judgment record is not a new memory layer and is not a `Node`.

It is an audit artifact recording how the system reached a Durable operation.

Suggested logical shape:

```yaml
JudgmentRecord:
  id:
  created_at:

  input_semantic_ids:
  candidate_durable_identities:

  proposal:
    operation:
    target_identity:
    kind:
    statement:
    attributes:
    evidence_ids:
    rationale:
    confidence:

  verification:
    support_assessment:
    unsupported_claims:
    missing_context:
    confidence:

  challenge:
    counter_evidence_ids:
    contradictions:
    scope_limitations:
    alternative_interpretations:

  revision:
    final_operation:
    final_target_identity:
    final_kind:
    final_statement:
    final_attributes:
    final_evidence_ids:
    final_confidence:

  model_runs:
    proposer:
    verifier:
    challenger:
    reviser:

  final_engine_action:
    operation:
    identity:
    version:
    modifications:
    rejection_reason:
```

Exact storage representation remains an implementation decision.

The contract is that the full process must be inspectable.

---

## Evidence Grouping

M3.1 does not introduce a fixed structural support unit such as:

* chapter
* document
* meeting
* trace run
* journal day

These boundaries are useful metadata but are not reliable definitions of independent evidence.

Evidence grouping is a semantic judgment.

The system may determine that:

* several passages describe one event;
* one trace contains several independent findings;
* several traces describe the same underlying failure;
* a single major decision is sufficient to produce durable knowledge;
* repeated trivial observations do not produce durable knowledge.

Evidence groups may be represented inside the `JudgmentRecord`.

They are not initially persisted as first-class knowledge nodes.

Example:

```yaml
evidence_groups:
  - semantic_ids:
      - sem_12
      - sem_18
    interpretation:
      "Two descriptions of the same production incident."

  - semantic_ids:
      - sem_31
    interpretation:
      "A separate later incident showing the same failure mode."
```

The model may use evidence independence as one consideration, but the engine does not enforce a numeric threshold as the definition of durability.

---

## Automated Roles

The pipeline should separate model responsibilities.

These may use separate prompts, separate calls, or separate models.

### 1. Proposer

The proposer identifies candidate Durable changes.

Input:

* relevant Semantic records;
* active Durable memories;
* selected historical context.

Output:

* `ADD`, `UPDATE`, `MERGE`, or `NO_OP`;
* candidate statement;
* evidence mapping;
* candidate identity match;
* rationale;
* confidence.

The proposer should prefer `NO_OP` when no meaningful long-term change is supported.

### 2. Verifier

The verifier asks:

> Does the cited evidence actually support the proposed statement?

It checks:

* whether each claim is grounded;
* whether scope exceeds evidence;
* whether the proposal combines unrelated events;
* whether evidence is duplicated;
* whether an existing Durable identity already expresses the same knowledge.

The verifier must not merely restate the proposal.

### 3. Challenger

The challenger actively searches for reasons the proposal may be wrong or incomplete.

It looks for:

* contradictory Semantic records;
* counterexamples;
* temporal changes;
* contextual exceptions;
* alternative interpretations;
* evidence that limits the statement to one phase, person, project, or condition.

The challenger is adversarial by design.

### 4. Reviser

The reviser receives:

* original proposal;
* verifier findings;
* challenger findings;
* existing Durable state.

It returns the final recommended operation.

Possible outcomes:

```text
ADD
UPDATE
MERGE
NO_OP
```

It may narrow or qualify a statement.

Example:

Initial proposal:

```text
She always prioritized family over career.
```

After challenge:

```text
During her early adult life, she frequently prioritized family stability over career advancement.
```

---

## Commit Policy

The engine commits only the reviser's final recommendation after invariant validation.

The engine must verify:

* referenced Semantic records exist;
* referenced Durable identities exist where required;
* layer relationships are valid;
* duplicate identities are not created;
* retired nodes are not treated as active targets;
* evidence references are valid;
* version chains remain linear;
* merge lifecycle is preserved.

The engine records both:

* the model's final recommendation;
* the action actually committed.

This distinction is required because engine invariants may alter the operation.

---

## Confidence

Confidence is model-proposed metadata, not truth probability.

It may be useful for:

* prioritizing future re-evaluation;
* deciding how much evidence to retrieve;
* Explorer display;
* benchmark analysis;
* selecting candidates for challenge.

M3.1 should not use one universal confidence threshold to define durability.

Confidence values must include their source:

```text
proposer confidence
verifier confidence
challenger confidence
final confidence
```

---

## Retrieval for Consolidation

The system must not send the entire knowledge base to the model.

Candidate retrieval should produce a bounded working set.

For each consolidation run:

```text
new Semantic records
        +
related active Durable memories
        +
related historical Semantic evidence
        +
potential counter-evidence
```

Candidate generation may use:

* vector similarity;
* lexical search;
* subject/entity overlap;
* time range;
* provenance links;
* existing Durable evidence neighborhoods.

These retrieval mechanisms generate candidates only.

They do not determine the final semantic judgment.

---

## Incremental Processing

M3.1 should process new Semantic records incrementally.

A run should not automatically reconsider every Durable node.

Suggested process:

```text
new Semantic records
        ↓
retrieve affected Durable candidates
        ↓
run judgment pipeline
        ↓
commit local changes
```

Periodic full reconsideration may be introduced later as a separate maintenance strategy.

M3.1 must preserve the distinction between:

* incremental update;
* periodic rebuild;
* targeted re-evaluation.

---

## Stability and Minimal Change

The desired behavior is:

```text
ordinary new evidence
→ mostly NO_OP
```

```text
meaningful reinforcing evidence
→ evidence update or qualified UPDATE
```

```text
major contradictory evidence
→ UPDATE, split, retire, or MERGE
```

The system should avoid changing Durable text solely because another wording is possible.

Exact string equality remains a deterministic baseline.

Semantic equivalence becomes part of the verifier/reviser judgment.

A new version should represent a meaningful knowledge change, not stylistic paraphrasing.

---

## Contradictions

Contradiction handling is model-guided but engine-recorded.

Possible outcomes include:

### Qualify

```text
The pattern applies primarily during the project's early phase.
```

### Update

```text
The team's deployment strategy changed after the 2025 incident.
```

### Split

```text
Early-stage behavior
Late-stage behavior
```

### Preserve competing interpretations

When evidence cannot support one definitive judgment, the system may retain multiple Durable nodes with explicit conflict relationships.

### NO_OP

The new evidence may not materially affect the existing judgment.

M3.1 should not force every contradiction into one synthesized statement.

---

## Decision Provenance

LYR must answer two different questions.

### Knowledge provenance

> Which Semantic records support this Durable statement?

```text
Durable
    ↓
Semantic
    ↓
Source
```

### Judgment provenance

> Why did the system decide to create or change this Durable statement?

```text
Durable version
    ↓
JudgmentRecord
    ├── proposal
    ├── verification
    ├── challenge
    ├── revision
    └── final engine action
```

Both provenance paths are required.

---

## Deterministic Baseline

`RecurrenceConsolidator` remains in the system.

Its role is explicitly limited to:

* offline operation;
* deterministic unit tests;
* reproducibility control;
* comparison baseline;
* infrastructure validation.

It must not be presented as LYR's definition of durability.

The benchmark should compare the automated judgment pipeline against this baseline.

---

## Evaluation

M3.1 introduces a human-labeled judgment benchmark.

The benchmark evaluates semantic consolidation decisions rather than final question answering.

### Unit of Evaluation

Input:

```text
active Durable memories
+
new and historical Semantic records
```

Expected output:

```text
operation
identity match
statement
evidence selection
counter-evidence handling
```

### Required Cases

#### Case 1 — Duplicate descriptions

Several Semantic records describe the same event.

Expected:

* recognize one underlying evidence instance;
* avoid treating duplicated text as independent support;
* avoid unnecessary Durable creation.

#### Case 2 — Independent reinforcing evidence

Separate events support the same long-term conclusion.

Expected:

* form or strengthen a Durable judgment;
* preserve distinct provenance.

#### Case 3 — Significant one-off event

One major decision or event has durable future importance.

Expected:

* allow `ADD` without recurrence.

#### Case 4 — Frequent noise

A trivial observation appears repeatedly.

Expected:

* `NO_OP`.

#### Case 5 — Contradictory evidence

New evidence conflicts with an active Durable statement.

Expected:

* qualify, update, split, or explicitly preserve conflict;
* not silently ignore the contradiction.

#### Case 6 — Identity match

New evidence belongs to an existing Durable identity.

Expected:

* `UPDATE` or `NO_OP`;
* no duplicate identity.

#### Case 7 — Paraphrase stability

The model proposes semantically equivalent wording.

Expected:

* no new version unless meaning materially changes.

#### Case 8 — Unsupported generalization

The proposal extends beyond the cited evidence.

Expected:

* verifier rejection or narrowed revision.

#### Case 9 — Merge

Two active Durable memories represent the same knowledge.

Expected:

* one active identity;
* one retired identity;
* complete retained history.

---

## Metrics

### Operation Accuracy

Correctness of:

```text
ADD / UPDATE / MERGE / NO_OP
```

### Identity Resolution Accuracy

Whether the proposal correctly matches an existing Durable identity.

### Evidence Precision

Fraction of selected evidence that genuinely supports the judgment.

### Evidence Recall

Fraction of relevant supporting evidence included.

### Counter-Evidence Recall

Whether material contradictions and exceptions were surfaced.

### Statement Groundedness

Whether all significant claims are supported by cited Semantic evidence.

### Scope Calibration

Whether the statement is appropriately qualified by time, subject, phase, and context.

### Minimal Change

Whether semantically unchanged knowledge avoids version churn.

### Provenance Completeness

Whether all committed operations include both knowledge and judgment provenance.

### Reproducibility

Variation across repeated runs with fixed inputs and model configuration.

---

## Human Labels

Human labels are required for evaluation, but not for production operation.

The product remains automated.

Human involvement is limited to:

* creating benchmark fixtures;
* evaluating system quality;
* improving prompts and policies;
* conducting research experiments.

Production users are not expected to accept, reject, or edit routine Durable judgments.

---

## Failure Handling

The engine must fail safely.

Examples:

### Invalid evidence reference

Reject the proposal and persist the failed judgment attempt.

### Malformed model output

Retry within configured limits, then record failure without mutating Durable state.

### Verifier and proposer disagreement

Pass both results to the reviser.

### Unresolved uncertainty

Prefer `NO_OP` or a qualified low-confidence judgment over an unsupported strong claim.

### Provider outage

Preserve pending work for later retry; do not fall back silently to a semantically weaker policy.

---

## Model Configuration

The pipeline remains pluggable.

Possible configurations:

### Single-model, multi-role

One provider and model with separate prompts for proposer, verifier, challenger, and reviser.

### Multi-model

Different models for generation and challenge.

### Strong-model plus small verifier

A strong model proposes; a smaller model performs bounded support checks.

### Deterministic baseline

No LLM; recurrence-based structural policy.

Every JudgmentRecord must store:

* provider;
* model identifier;
* prompt version;
* parameters;
* input IDs;
* output schema version;
* run ID.

---

## Privacy and Data Boundaries

LYR may process:

* private journals;
* company meetings;
* debug traces;
* personal archives.

M3.1 must keep provider access explicit.

The system should support:

* provider configuration;
* local or self-hosted model adapters;
* data redaction hooks;
* source-level access controls in future versions.

No model provider should be embedded into the core Durable semantics.

---

## Implementation Sequence

### M3.1-A — Judgment Contract

Implement:

* `JudgmentRecord`;
* role-specific proposal schemas;
* persistence contract;
* decision provenance linkage.

Do not yet add the full multi-pass pipeline.

### M3.1-B — Propose and Verify

Implement:

```text
Proposer
→ Verifier
→ Reviser
```

Challenger may initially share the verifier path.

### M3.1-C — Counter-Evidence Retrieval

Add explicit retrieval and challenge of contradictory evidence.

### M3.1-D — Evaluation Dataset

Create the initial manually labeled benchmark fixtures.

### M3.1-E — Baseline Comparison

Compare:

* recurrence baseline;
* single-pass LLM;
* propose–verify–revise;
* propose–verify–challenge–revise.

---

## Success Criteria

M3.1 is successful when LYR can demonstrate that:

1. one important event may form Durable knowledge without recurrence;
2. repeated trivial observations can remain `NO_OP`;
3. duplicated descriptions are not mistaken for independent evidence;
4. contradictions cause qualification or revision;
5. semantically unchanged knowledge avoids unnecessary versions;
6. every committed Durable version has complete knowledge provenance;
7. every committed operation has complete judgment provenance;
8. the automated multi-pass pipeline outperforms the recurrence baseline on a human-labeled consolidation dataset.

---

## Out of Scope

M3.1 does not include:

* Cognitive Memory;
* user approval workflows;
* model fine-tuning;
* full Explorer UI;
* autonomous prompt learning;
* organization-wide access control;
* formal truth guarantees;
* automatic replacement of all existing consolidation policies.

---

## Open Questions

1. Should `JudgmentRecord` be stored in the primary database or an append-only execution log?

2. Should evidence grouping be stored explicitly inside the judgment or derived from the model rationale and evidence mapping?

3. When should a low-confidence Durable judgment be committed rather than deferred?

4. Should competing interpretations be represented as separate Durable nodes or as one node with alternatives?

5. How should semantic-equivalence detection distinguish paraphrase from meaningful scope change?

6. How often should active Durable judgments be reconsidered without new direct evidence?

7. Should proposer and challenger use different models to reduce correlated errors?

8. How should retrieval find counter-evidence without scanning the full corpus?

---

## Milestone Outcome

At the end of M3.1, LYR will no longer equate recurrence with durability.

It will maintain Durable knowledge through an automated, inspectable process:

```text
Propose
    ↓
Verify
    ↓
Challenge
    ↓
Revise
    ↓
Commit
```

The result is not guaranteed truth.

It is a stable, versioned, evidence-backed judgment that can be automatically revised as new information arrives.
