# LYR M3.2 Design — Generic Knowledge Explorer

**Status:** Proposed
**Stage:** M3.2 (bridge between *forming* durable knowledge and *forming* cognition)
**Prerequisite:** M3.1 complete

---

## 0. North Star (read this first)

LYR is **not** a Book Explorer, a Diary Explorer, or a Git Explorer. LYR is a
**generic long-term memory system** — a computational account of how an intelligent
agent accumulates experience, maintains long-term coherence, and forms cognition.

Every concrete subject — a book, a diary, a company's history, a git repository, a
medical record, a parenting log — is a **validation domain**, never the center. The
core representation (`Source → Semantic → Durable → Cognitive`, one `Node` shape,
one provenance walk) is domain-agnostic *by construction*.

Two questions must stay separated, forever:

| | Question | Answer |
|---|---|---|
| **A — research** | *What is a generic long-term memory system?* | LYR |
| **B — demo** | *How do we demonstrate it?* | a Book (first), then others |

M3.2 is about **B in service of A**. Its real subject is not "exploring a book" — it
is proving that **one generic memory representation stays explorable across
fundamentally different domains with no core-algorithm changes.**

---

## 1. Motivation

M3.1 solved *forming* durable knowledge, and did so **generically**: the same builder,
unchanged, ran across four heterogeneous domains (memoir, meeting notes, financial
report, git history — M3.1-E). But a user never interacts with one `JudgmentRecord`.
Real collections hold hundreds of semantic memories and dozens-to-hundreds of durable
memories.

M3.2 extends the genericity M3.1 proved for the *builder* to the *navigation* layer:
the first user-facing way to explore an entire durable knowledge space — and evidence
that **the same explorer works across domains the same way the same builder did.**

---

## 2. Goal

Not to answer questions. Not to summarize. Rather:

> Demonstrate that **one generic long-term-memory representation can be explored
> consistently across fundamentally different domains** — and that a user can
> gradually understand any of them.

Closer to **exploring Wikipedia** than chatting with an LLM. A Book is the first
demonstration; it must never become the design center.

---

## 3. Design principles

- **P1. Exploration before conversation.** Users browse; conversation is optional.
- **P2. Knowledge first.** The UI exposes *knowledge* — not prompts, agents, or chains.
- **P3. Progressive disclosure.** Start with large concepts; every click reveals more; never dump hundreds of memories at once.
- **P4. Everything remains explainable.** Every concept traces `Durable → Semantic → Source`. Nothing appears without provenance.
- **P5. Domain-agnostic core (the load-bearing one).** The explorer consumes a
  **generic knowledge index** derived from the layer structure itself — entity /
  event / relationship kinds (Semantic) and durable kinds (Durable) — *never*
  domain-specific concepts hardcoded for "books." If a rule only works for books, it
  does not belong in the core.

---

## 4. Validation domains (not "the Book domain")

Version 1 stands the explorer up over **one Book** as the first demo — but the
milestone is only complete when the **same explorer, with no core changes**, also
stands up over at least two *fundamentally different* domains. Reuse the M3.1-E
domains so genericity is measured, not asserted, e.g.:

```
Book   ·   Git repository   ·   Financial report
```

If all three are explorable through one representation and one UI, the milestone has
demonstrated **generic**, not **book-specific**. (Future demos — diary, company
history, medical record, parenting log — follow the *same* template and must never
require a core change.)

---

## 5. User experience

The landing becomes: **Choose a domain → Explore.** Instead of a search box, the user
first sees entry points **derived from the generic node taxonomy** (so they adapt per
domain automatically):

**People · Ideas · Events · Places · Themes · Lessons**

- *People / Places* ← semantic entities · *Events* ← semantic events ·
  *Ideas / Themes / Lessons* ← durable kinds.
- The same taxonomy renders a book's characters, a repo's contributors + subsystems,
  or a report's entities + risks — **no per-domain UI.**

---

## 6. Exploration

Always moves from high-level concepts *toward* evidence:

```
People → <entity> → Timeline → Related Events → Durable Memories → Source Evidence
Themes → <theme>  → related durable memories → supporting evidence → conflicting evidence
```

---

## 7. Durable organization (navigation only)

The first **organization** layer over durable memories — *not* cognition:

```
N Durable Memories → grouped → <clusters derived from the memories themselves>
```

Groups exist **only for navigation**. They are not new knowledge, they do **not**
become `Node`s, and the grouping method is **domain-agnostic** (derived from the
durable memories, not a hand-authored per-book taxonomy).

---

## 8. Judgment integration

Every durable memory stays clickable; selecting one opens the existing **Judgment
Explorer**:

```
Knowledge Explorer → Durable Memory → Judgment Explorer
```

The M3.1 Judgment Explorer becomes a **developer-level drill-down**, not the primary
interface.

---

## 9. Non-goals

Cognition · theory formation · long-term reasoning · agent planning · chat ·
recommendations · memory editing · **any domain-specific special-casing.** The goal is
*understanding existing knowledge, generically.*

---

## 10. Success criteria

**Primary (genericity):** the **same** explorer, over the **same** representation,
with **no core-algorithm changes**, lets a first-time user explore **≥ 2–3
fundamentally different domains** (e.g. Book, Git, Financial).

**Per domain,** without asking a single question, a first-time user can: understand
what the subject is about; discover important people/entities; discover important
ideas/themes; understand how ideas evolved; inspect why any durable memory exists; and
trace any conclusion back to source.

**Falsifier:** if making a second domain work requires touching core logic (not just
feeding it different data), the representation is *not yet* generic — that is a
finding, not a failure to paper over.

---

## 11. Why this comes before M4

M4 asks *how do durable memories become cognition?* M3.2 asks *how do humans navigate
durable memories?* Until users can comfortably explore durable knowledge, there is no
practical way to evaluate whether higher-level cognition is useful. M3.2 also
**protects M4**: building a generic explorer first forces the question *"can a real
user understand what this new layer adds?"* — so cognition is built as something
inspectable, not an abstraction only its author can read.

And M4 must be framed generically too. Not "book cognition" — but:

> *What persistent internal state lets an intelligent system remain coherent over
> years?*

— a question that applies equally to a person, a company, a book, an agent, a
project, or a medical record.

---

## 12. Future direction

```
<any domain> → Semantic → Durable → Knowledge Explorer → Cognition → Cognitive Explorer
```

Cognition emerges as an additional **explorable layer** over durable knowledge — the
same generic representation, one more layer up. In the eventual paper, Book / Git /
Company / Diary appear not as four products but as **four validation domains for one
system.**
