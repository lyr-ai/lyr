# LYR M3.1-B.1 Design — Judgment Contract Hardening

**Status:** Implemented
**Stage:** M3.1-B.1
**Prerequisite:** [M3.1-B (Minimal Durable Builder)](./M3.1-B-minimal-durable-builder.md)

---

## 1. Motivation

M3.1-B demonstrated the first end-to-end durable judgment pipeline and proved the
architecture viable. Review then found several places where the *implementation*
was looser than the *theory*. This milestone strengthens those contracts only. **No
new reasoning capability, no verifier, no added intelligence** — the goal is to make
the existing pipeline trustworthy before increasing its complexity.

Public Builder API (`JudgmentBuilder.update(...) -> JudgmentResult`) is unchanged.

---

## 2. Goals

- **G1.** Every judgment attempt has a globally unique identity — executions never
  overwrite one another.
- **G2.** JudgmentRecords are genuinely immutable, not immutable-by-convention.
- **G3.** Model output is preserved exactly, distinct from the builder's
  interpretation and the engine's action.
- **G4.** Implementation matches documented guarantees (esp. replay).

---

## 3. Non-Goals

Verifier · Challenger · multi-round reasoning · prompt improvements · better durable
judgment · Cognitive layer · retrieval · performance.

---

## 4. Design changes (as implemented)

### 4.1 Attempt identity vs. semantic fingerprint

`judgment_id` is now a **globally unique, time-ordered execution id** —
ULID-style: 48-bit millisecond timestamp + 80 bits randomness, Crockford base32,
zero-dependency (`new_judgment_id()` in `lyr/durable/judgment.py`). It never repeats,
so an attempt can never overwrite another in the append-only log.

`judgment_fingerprint` is a new, **content-derived** id (`jfp_…`, from operation +
statement + sorted evidence + candidate identities). It *may* repeat across
executions — that is how duplicate attempts are detected without conflating them.

The durable version's back-reference (`node.attributes["judgment_id"]`) points to
the unique execution id. Node identity/version remain content-addressed and
unaffected (attributes are excluded from a node's content id), so idempotent
rebuilds still hold.

### 4.2 Raw model output preserved

`JudgmentRecord` now records four distinct stages:

```
raw_completion   → the LLM's exact output string (fences, chatter, and all)
parsed_payload   → the JSON dict the builder parsed out of it, or None
model_intent     → the normalized, id-resolved ModelProposal
final_engine_action → what the engine actually committed
```

Debugging never has to guess what the model produced, and old outputs can be
re-parsed if parsing rules later change.

### 4.3 Structural immutability

`JudgmentRecord`, `ModelProposal`, `EngineAction`, and the new `EvidenceGroup` are
**frozen dataclasses** with **tuple** collections instead of lists. Once built and
appended to the store, a record cannot be mutated. (`JudgmentResult.updated_durable`
is intentionally the live `Node`, not frozen — only the audit record is immutable.)

### 4.4 Replay semantics (corrected — G4)

The authoritative statement, superseding the stronger wording in
[M3.1-A §10](./M3.1-A-judgment-contract.md#10-replay):

> **Durable versions are traceable back to the judgment that created them** — via
> the `judgment_id` back-reference. This is *provenance*.
>
> Full event-sourced reconstruction of durable state **solely from
> JudgmentRecords** is **not** implemented. It is a candidate for a future
> milestone, not a current guarantee.

Documentation and code no longer claim deterministic reconstruction the
implementation does not provide.

### 4.5 Evidence-group validation

Model-proposed `evidence_groups` are validated into immutable `EvidenceGroup`
objects: referenced indices must be **in range**, are **de-duplicated** (order
preserved), and are **resolved to real semantic ids** (`semantic_ids`). An audit
artifact can no longer cite a record that was not in the input.

### 4.6 Complete MERGE coverage

The suite now covers the full MERGE lifecycle: valid merge (fold + retire), invalid
merge target (REJECT), duplicate/self/invalid merge indices (de-duplicated),
superseded tombstoning (`status=retired`, `merged_into`), history/provenance
preservation, and engine-action correctness.

### 4.7 Single canonical prompt source

The builder prompt lives in exactly one versioned file,
`lyr/durable/prompts/durable_builder_v1.md`, loaded once via `importlib.resources`
and exposed as `lyr.durable.PROMPT` / `PROMPT_VERSION`. The builder (and the
`--builder` harness through it) use that single source, so prompt evolution happens
in one place. The step-by-step `experiments/prompts/durability_judgment_v1.md` is a
**separate reasoning-inspection artifact** (for reading how a model thinks), not the
builder contract, and is labeled as such.
