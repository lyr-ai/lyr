# LYR M3.2-A Design — Generic Navigation Formation

**Status:** Proposed
**Stage:** M3.2-A (experiment — **no UI**)
**Prerequisite:** M3.1 complete · [M3.2 umbrella](./M3.2-knowledge-explorer.md)

---

## 1. The question (and why it comes before any UI)

M3.2's umbrella goal is a *generic* knowledge explorer. Building a UI first would let a
**Book Explorer** quietly become the thing we test — and a book is *too easy* (it comes
with People, Places, Events, Themes for free). The real, falsifiable question is
smaller and harder, and needs **no interface**:

> **Can one generic algorithm turn durable memories into one navigation structure —
> across fundamentally different domains — with no domain-specific code?**

M3.1 proved the representation can *store* many domains. It did **not** prove the
representation can be *organized* the same way across them. That is this experiment.

Three distinct research questions, kept separate: M3 / M3.1 = **Formation**, M3.2 =
**Organization**, M4 = **Explanation**. M3.2-A owns the *formation of the organization
graph* — the graph, not its picture.

---

## 2. Scope — and the honest name

First deliverable is an **Evidence-Connectivity Baseline**, *not* "generic topic
formation." It is named for exactly what it can honestly do:

```
durable nodes
  → resolve evidence ancestry (durable → semantic → source)
  → connect durables that share semantic or source ancestry
  → connected components
  → NavigationGraph
```

It presupposes **nothing** about producing *useful* topics. Whether provenance
connectivity is even sufficient for organization is *itself* the thing under test (§7).

**Out of scope for the baseline** (adding any of these would make it impossible to know
what the structural signal alone provides): label-embedding similarity · LLM topic
assignment · hand-written keywords · grouping by domain metadata · any
people/theme/project category.

---

## 3. The falsifier

> If making a second domain's navigation work requires **domain-specific code** — an
> `if domain == "git"`, a book-only "Themes" rule, a per-domain grouping heuristic — the
> representation is **not** generic and M3.2-A has **failed**.

The grouping function receives `list[Node]` and **nothing else** — it is not told which
domain it is looking at, so it *cannot* special-case one. Success is *one code path*
run unchanged over every domain.

---

## 4. `form_navigation(nodes: list[Node]) -> NavigationGraph`

No `domain` in the input. Every connection stores its structural reason. Singletons are
produced honestly.

### Two-level edges (both generic — neither needs to know the domain)

- **`shared_semantic`** — two durables cite a common semantic record.
- **`shared_source`** — their semantic evidence traces (one hop down) to a common
  source/origin.

Every edge carries its justification, so the graph is itself explainable:

```json
{ "from": "dur_a", "to": "dur_b", "relation": "shared_source",
  "support": ["standup-2025-04-18"] }
```

### Entry points — generic facets only

Derived from the generic node taxonomy, never book concepts: entities
(`kind="entity"`), events (`kind="event"`), durable kinds
(`lesson`/`decision`/`pattern`/`fact`/…), time.

### Schema — allow a durable in MANY groups from day one

Real knowledge crosses ("Family over career" → Family, Career, Decision-patterns). Even
though the baseline's connected components happen to be disjoint, the **data model must
not** be `list[list[DurableNode]]`. Instead:

```
NavigationGraph
  durables:   [ {id, kind, statement, semantic_evidence, source_origins} ]
  groups:     [ {id, label, members: [durable_id, …]} ]      # members MAY overlap
  connections:[ {from, to, relation, support:[…]} ]           # durable ↔ durable, with reason
  entry_points:{ entity:[…], event:[…], durable_kind:{…} }    # generic facets
  metrics:    { n_durables, n_groups, compression }
```

A future overlapping organizer then needs no schema change.

---

## 5. Two phases — Phase 1 passing is NOT M3.2-A complete

### Phase 1 — Genericity sanity check (now; existing four domains)

memoir · meeting · financial · git. Verifies **implementation genericity** only:
same function, no `domain` argument, identical output schema, complete provenance,
reproducible, no domain branches, **singletons preserved honestly**.

> Phase 1 answers *"can one code path handle four kinds of input without looking at the
> domain?"* — it does **not** answer *"is the navigation useful?"*

### Phase 2 — Organizational adequacy (before any M3.2-B UI; richer corpus)

With only 3–5 durables per domain we cannot judge whether grouping *compresses*,
whether groups are internally coherent, whether a durable should belong to several
groups, whether the graph is more navigable than a flat list, or whether source
connectivity produces one giant meaningless component. A richer corpus is required
**before** M3.2-B — but we do **not** block Phase 1 on finding one.

---

## 6. Metrics

- **Compression** = `n_durables ÷ n_groups`. If 20 durables → 20 singletons,
  compression = 1.0: the algorithm is generic but has **no organizational value**.
- **Coherence** (Phase 1: manual label per group — `coherent` / `mixed` / `singleton`).
  Guards the specific failure where everything from one book/long meeting shares a
  source and collapses into one giant cluster — *structurally connected, navigationally
  useless.*

---

## 7. Pre-registered outcomes (all three are real results — do not tune the algorithm toward any)

- **A — few, coherent groups.** Shared evidence/source ancestry is enough to organize.
  → grow the corpus and re-check (Phase 2).
- **B — mostly singletons.** *Provenance connectivity is insufficient for navigation
  topics.* → research a **generic semantic** organizer next — never a domain-specific one.
- **C — one giant mixed component.** Source overlap is too coarse (a book / long meeting
  glues everything together). → redefine the support unit or connection granularity.

None of these is a failure to hide. Modifying the algorithm to *look* like a knowledge
map would destroy the experiment.

---

## 8. Success criteria (Phase 1)

- one `form_navigation(nodes)` — **no domain arg, no domain branch** — runs unchanged
  over all four domains;
- identical output schema across domains; every `group → durable → semantic → source`
  path resolves (P4 preserved); connections carry their reason;
- reproducible; singletons reported honestly; compression + coherence reported;
- the observed outcome (A / B / C) recorded as-is.

**Then, and only then** (and after Phase 2), M3.2-B is the easy part:
`Explorer = render(NavigationGraph)`.

---

## 9. Deliverables

- `lyr/navigation/`: `NavigationGraph` + a generic `form_navigation`.
- a Phase-1 runner producing the four graphs as data + the genericity check + metrics.
- deterministic tests.
- a findings note (EXPERIMENT-M3.2-A) recording the A/B/C outcome.

No web page. That is M3.2-B.
