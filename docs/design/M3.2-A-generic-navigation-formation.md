# LYR M3.2-A Design — Generic Navigation Formation

**Status:** Proposed
**Stage:** M3.2-A (experiment — **no UI**)
**Prerequisite:** M3.1 complete · [M3.2 umbrella](./M3.2-knowledge-explorer.md)

---

## 1. The question (and why it comes before any UI)

M3.2's umbrella goal is a *generic* knowledge explorer. But building a UI first would
let a **Book Explorer** quietly become the thing we test — and a book is *too easy*
(it comes with People, Places, Events, Themes for free). The real, falsifiable
question is smaller and harder, and it needs **no interface**:

> **Can one generic algorithm turn durable memories into one generic navigation
> structure — across fundamentally different domains — with no domain-specific code?**

M3.1 already proved the representation can *store* many domains. It did **not** prove
the representation can be *organized* the same way across them. That is this
experiment.

Three distinct research questions, kept separate:

| Stage | Question |
|---|---|
| M3 / M3.1 | Knowledge **Formation** — what becomes durable? |
| **M3.2** | Knowledge **Organization** — how is durable knowledge structured for navigation? |
| M4 | Knowledge **Explanation** — how does it become cognition? |

M3.2-A owns *Organization*, and only the *formation* half of it — the graph, not its
picture.

---

## 2. Scope

- **In:** one function, `durable (+ semantic) → NavigationGraph`, run over multiple
  domains; the graph inspected as data (JSON / printed), not rendered.
- **Out:** any UI, any web page (that is M3.2-B: `render(NavigationGraph)`), cognition,
  chat, editing.

Splitting the milestone this way keeps **the UI from hijacking the research** — the
Explorer becomes a pure function of a graph the experiment has already validated.

---

## 3. The falsifier (the whole point)

> If making a second domain's navigation work requires **domain-specific code** —
> a `if domain == "git"`, a book-only "Themes" rule, a per-domain grouping heuristic —
> then the representation is **not** generic, and M3.2-A has **failed**.

Success is *one code path*, run unchanged over every domain. A failure here is a
genuine finding (the representation needs a missing generic facet), not something to
patch with a special case.

---

## 4. What "navigation" is, generically

A `NavigationGraph` is built **only** from facets that exist in *every* domain because
they are part of the generic `Node`/layer structure — never from concepts invented for
one domain:

- **Entry points** — derived from the generic node taxonomy:
  - *entities* (semantic `kind="entity"`) → People / Places / Subjects
  - *events* (semantic `kind="event"`) → Events / Timeline
  - *durable kinds* (`lesson` / `decision` / `preference` / `pattern` / `fact` / …) → Ideas / Lessons / Themes
  - *time* (`created_at`) → chronology
- **Topics** — clusters of durable memories, formed by a **domain-agnostic** rule
  (below). Topics are *navigation only*: not `Node`s, not new knowledge.
- **Edges** — the always-explainable spine, unchanged from M3.1:
  `Topic → Durable → Semantic evidence → Source`.

If a facet only exists for books, it does not go in the graph.

---

## 5. The generic grouping rule (the key design decision)

How are durable memories clustered into topics *without domain knowledge*? Three
candidates; **A/B are structural, the recommended start**, because a pure-structure
rule *cannot hide* a domain-specific branch:

- **(A) Shared-evidence co-citation.** Two durables are linked if their evidence sets
  overlap (they cite common semantic records, or — one hop down — common sources).
  Topics = connected components / communities. Deterministic, provably generic.
- **(B) Shared-entity linkage.** Two durables are linked if they reference the same
  semantic entity. Deterministic, generic. (Degenerate where entity extraction is
  thin — see §7.)
- **(C) Model-driven labeling *only*.** Structure comes from A/B; an LLM assigns a
  short human label to each cluster (same prompt for every domain). The *structure*
  stays deterministic and generic; naming is a separable, optional concern.

**Recommendation:** ship **(A)** first (deterministic, offline, the strongest
falsifier), with cluster labels initially taken from the cluster's representative
durable statement (no model needed). Add (C) later purely for prettier labels — never
for structure.

**Anti-requirement:** the grouping function receives `list[Node]` and nothing else. It
is not told which domain it is looking at. If it *can't* be told the domain, it can't
special-case one.

---

## 6. The experiment

Run the **same** `form_navigation(nodes)` over the four M3.1 domains — **memoir,
meeting notes, financial report, git history** — and compare the graphs:

```
memoir    durables → topics {family, letters, financial-risk, …}
meeting   durables → topics {billing sunset, DB reversal, CI flakiness, …}
financial durables → topics {acquisition, dividend, impairment, …}
git       durables → topics {gRPC migration, auth fragility, redis lesson, …}
```

The topic *names* do not matter. What matters is that **one function produced all four
graphs**, each with the same shape (entry points + topics + the `Topic → Durable →
Semantic → Source` spine), with **zero domain-specific branches**.

**Report:**
- the four graphs (as data);
- a genericity check: one code path, no `if domain == …`, identical schema out;
- honest limitations (§7).

---

## 7. Known limitations to state, not hide

- **Scale.** The M3.1 fixtures yield only ~3–5 durable memories per domain, so
  clusters will often be singletons — the graph is *thin*. That tests **genericity of
  the method**, not navigation-at-scale (the umbrella's "120 memories → 5 groups" is
  future, larger-corpus work). Say so; don't dress a 4-node graph as a knowledge map.
- **Entity sparsity.** The fixtures are mostly `event`-kind records with little entity
  extraction, so People/Places entry points will be thin in some domains. That is a
  property of the *data*, not a domain-specific code path — and itself a finding about
  what richer generic extraction M3.2 will want.

---

## 8. Success criteria

- one `form_navigation(nodes) → NavigationGraph`, **no domain argument, no
  domain-specific branch**, runs unchanged over all four domains;
- every domain yields the same graph schema (entry points + topics + explainable edges);
- every topic → durable → semantic → source path resolves (P4 preserved);
- limitations reported honestly.

**Then, and only then,** M3.2-B is the easy part: `Explorer = render(NavigationGraph)`
— the UI renders a structure the experiment has already proven generic, so the UI can
never hijack the research.

---

## 9. Deliverables

- `lyr/navigation/` (or similar): `NavigationGraph` type + a generic `form_navigation`.
- an experiment runner producing the four graphs as data, plus the genericity check.
- tests (deterministic → unit-testable offline).
- a short findings note (EXPERIMENT-M3.2-A) once run.

No web page. That is M3.2-B.
