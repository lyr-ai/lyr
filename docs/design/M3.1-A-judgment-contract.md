# LYR M3.1-A Design — Judgment Contract

**Status:** Draft
**Stage:** M3.1-A
**Goal:** Establish immutable judgment recording before implementing automated durable knowledge formation.

---

## 1. Motivation

The M3 layer introduced the concept of Durable Knowledge, but the process that transforms Semantic knowledge into Durable knowledge is still experimental.

Rather than immediately implementing Proposer, Verifier, Challenger, and Reviser, the system first needs an immutable record describing every knowledge formation attempt.

This document defines that record.

The objective is **not** to improve judgment quality.

The objective is to make every judgment:

* reproducible
* auditable
* replayable
* attributable

---

## 2. Scope

This milestone only introduces the infrastructure.

It does **not** implement:

* Proposer
* Verifier
* Challenger
* Reviser
* Cognitive Builder
* Confidence scoring
* Automatic durable formation

Those remain future milestones.

---

## 3. Design Goals

The Judgment Contract must satisfy the following principles.

### G1. Every attempt is preserved

Successful judgments, rejected judgments, and NO_OP decisions are all recorded.

Nothing disappears.

### G2. Durable state is explainable

Every durable version must be traceable back to the judgment that created it.

### G3. Replay is deterministic

The engine must be able to reconstruct the complete durable state without invoking an LLM.

Replay depends only on recorded engine actions.

### G4. Model reasoning is preserved

The model's proposed interpretation is stored exactly as produced.

The engine may reject or modify it, but it is never overwritten.

---

## 4. Architecture

```
Semantic Nodes
        │
        ▼
 JudgmentRecord
        │
        ▼
 Engine Commit
        │
        ▼
 Durable Version
```

JudgmentRecord acts as the immutable bridge between Semantic and Durable.

---

## 5. JudgmentRecord

A JudgmentRecord represents one attempt to transform semantic evidence into durable knowledge.

Each record is immutable.

Suggested fields:

```
judgment_id

created_at

candidate_semantic_ids

target_durable_id

proposal

evidence_groups

model_intent

final_engine_action

model_config
```

---

## 6. Model Intent

The model proposes one intended operation.

Supported operations:

* ADD
* UPDATE
* MERGE
* NO_OP

These represent the model's recommendation only.

The engine is not required to execute them.

---

## 7. Engine Action

The engine records the actual committed result.

Suggested fields:

```
operation

node_id

identity

version

rejection_reason
```

Examples:

* ADD
* UPDATE
* MERGE
* REJECT
* NO_OP

Engine actions define system history.

They are deterministic.

---

## 8. Durable Linkage

Every committed durable version stores exactly one back-reference.

```
judgment_id
```

This allows:

Durable Version

→ JudgmentRecord

→ Semantic Evidence

Rejected or NO_OP judgments do not create this linkage.

---

## 9. Storage Principles

JudgmentRecord is:

* immutable
* append-only
* stored in the primary database
* not modeled as a Node

Evidence groups are stored locally inside each JudgmentRecord.

They do not receive independent identities.

---

## 10. Replay

> **Corrected by [M3.1-B.1 §4.4](./M3.1-B.1-judgment-contract-hardening.md).** The
> claims in this section overstate what the implementation guarantees. What holds
> today is *provenance*: **durable versions are traceable back to the judgment that
> created them** (via `judgment_id`). Full event-sourced reconstruction of durable
> state *solely* from JudgmentRecords is **not** yet implemented and is deferred to
> a future milestone. The original text is kept below as the historical record.

Replay reconstructs durable knowledge exclusively from recorded engine actions.

Replay never invokes an LLM.

This guarantees deterministic reconstruction.

Model replay remains best-effort and is outside the scope of this milestone.

---

## 11. Success Criteria

M3.1-A is complete when the following conditions hold.

* Every durable judgment creates an immutable JudgmentRecord.
* Rejected and NO_OP judgments are preserved.
* Every durable version can be traced back through a single judgment_id.
* Durable state can be deterministically reconstructed without calling a model.
  *(Corrected by M3.1-B.1 §4.4: only back-traceability is implemented; full
  reconstruction solely from JudgmentRecords is deferred.)*
* No existing Semantic or Durable behavior changes.

---

## 12. Out of Scope

This milestone intentionally postpones:

* Proposer implementation
* Verifier implementation
* Challenger implementation
* Reviser implementation
* Cognitive Builder
* Confidence estimation
* Global EvidenceGroup identities
* Benchmark evaluation
* Knowledge quality improvements

These will be introduced incrementally in later M3.1 milestones.

---
