# LYR M3.1-C0 — Durability Verification Task

**Status:** Proposed (task definition — **frozen before implementation**)
**Stage:** M3.1-C0
**Prerequisite:** [M3.1-B.2 findings](../../experiments/evaluation/EXPERIMENT-M3.1-B.2.md) + [durability-v1 benchmark](../../experiments/evaluation/benchmark/durability-v1/)

---

## Purpose

Freeze *what durability verification is* before any verifier is built. Without a
frozen task, a "verifier" drifts — reject coffee today, check grounding tomorrow,
scope next, contradiction later — until it is just a second Builder. This document
fixes the boundary so M3.1-C implements a **verifier**, not another proposer.

It answers exactly four questions and fixes one standing principle. It contains **no
architecture and no code.**

---

## 1. What may the verifier change?

**FROZEN — the verifier is a gate, not an editor.** Its only effect is to **veto** a
proposed durable write: turn a **KEEP into a REJECT**, so the engine commits `NO_OP`
instead of the proposed `ADD` / `UPDATE` / `MERGE`. One direction only: `KEEP → REJECT`.

It may **not**:
- rewrite the statement
- change the operation to a *different write* (e.g. `ADD → UPDATE`)
- change `kind`, evidence, scope, confidence, or identity
- create, merge, or split durable memories

*Rationale:* anything beyond veto re-does the Builder's or the engine's job. A gate
that can only reject cannot become a proposer.

---

## 2. What evidence may it use?

**FROZEN — the verifier inherits the Builder's judgment context; it never defines its
own input.** Concretely, two things:
1. the **JudgmentRecord** (proposed statement, `kind`, rationale, confidence, evidence ids), and
2. **the evidence the Builder legitimately used to make this proposal** — today the
   cited semantic nodes; whatever the Builder's visible input evolves into tomorrow,
   the verifier sees exactly that, no more.

It may **not** use:
- candidate durable memories — redundancy/merge is the Builder's concern, not persistence
- source records — layer isolation (consistent with M3: consolidators never read source)

*Rationale:* Builder and verifier share **one judgment context**, not a fixed node
*type*. Pinning the verifier to "semantic nodes" would shatter its boundary the moment
the Builder's input evolves; pinning it to "whatever the Builder saw" keeps the two in
lockstep. The rule stays the minimum needed to judge "is this, given its own evidence,
worth keeping?" — nothing that reaches across layers or re-decides what the Builder
already decided.

---

## 3. What question does it answer?

**FROZEN — exactly one:**

> **Should this proposed durable memory become long-term knowledge?**

It is **not** answering:
- Is it true? *(grounding is a separate concern)*
- Is it useful?
- Is it well written?
- Is it in scope / does it contradict something? *(separate concerns, separate stages)*

*Rationale:* every M3.1 stage asked exactly one question. This one asks about
**durability**, nothing else.

---

## 4. What outputs may it produce?

**FROZEN — a three-valued verdict:** `KEEP | REJECT | UNSURE`.

- **KEEP** → the proposed durable stands.
- **REJECT** → downgrade to `NO_OP`; the durable is not committed, but the attempt
  (and the verdict) are still recorded.
- **UNSURE** → **retention-biased**: treated as KEEP but flagged. The verifier never
  silently drops a memory it was not sure about.

The verdict is recorded as decision provenance (record shape is M3.1-C's problem, not
this document's).

**UNSURE is a temporary system state, not a third durability class.** Knowledge has
exactly two classes — **Durable** and **Transient**. UNSURE is *verification
confidence*, not a knowledge type: a flagged KEEP awaiting stronger evidence, never a
new memory layer. (This guards against UNSURE quietly growing into its own store.)

*Rationale:* three-valued so it can abstain on genuine borderlines (matching the
benchmark's `borderline`), while defaulting to conservative retention. A false KEEP is
cheaper to fix than a false REJECT: new evidence can still turn `KEEP → REJECT` later,
but a premature REJECT may mean the knowledge never re-enters the system at all.

> Open call (overridable): UNSURE defaults to retention (KEEP-but-flagged). The
> alternative — UNSURE defers to human review — is viable but breaks the "no routine
> user review" property. Frozen as retention-biased unless revised.

---

## 5. The verifier is stateless (standing principle)

**FROZEN.** The verifier judges **one proposed durable memory in isolation.** It does
**not** see:
- the history of previous verifications
- other pending judgments in the same batch
- any future candidate judgments

*Rationale:* the Builder generates candidates; the verifier accepts or rejects **one**
candidate. Statelessness is what stops it from slowly becoming *another planner* that
reasons across judgments — the same failure mode the evidence boundary (§2) guards
against, from the other side. Cross-judgment reasoning, if ever needed, is a separate
stage with its own task definition.

---

## Scope boundary (the thing being frozen)

The verifier judges **persistence, and only persistence.** If later we want grounding,
contradiction, or scope checks, each is a **separate stage with its own C0-style task
definition** — never an extension of this one. This is what stops the verifier from
becoming a second Builder.

---

## Evaluation mapping (against `durability-v1`)

For each benchmark case, the verifier emits `KEEP`/`REJECT`; scored vs.
`deserves_persistence`:

| verifier | label `no` | label `yes` |
|---|---|---|
| **REJECT** | ✅ true positive (the win: coffee, donuts, cloud-growth) | ❌ false negative (over-pruning) |
| **KEEP** | ❌ false positive (the failure to fix) | ✅ true negative |

`borderline` labels and `UNSURE` verdicts are excluded from strict scoring.

The single number M3.1-C must move: **false positives on the 5 `no` cases → down,
without creating false negatives on the 13 `yes` cases.**
