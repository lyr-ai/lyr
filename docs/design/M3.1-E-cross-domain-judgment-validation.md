# LYR M3.1-E Design — Cross-Domain Judgment Validation

**Status:** Proposed
**Stage:** M3.1-E (Empirical Validation)
**Prerequisite:** [M3.1-B.1 — Judgment Contract Hardening](./M3.1-B.1-judgment-contract-hardening.md)

---

## 1. Motivation

M3.1-B.1 completed the implementation of the minimal durable judgment pipeline and strengthened its contracts. The system now provides immutable JudgmentRecords, unique execution identities, preserved raw model outputs, validated evidence references, trustworthy audit artifacts, and deterministic engine behavior.

The engineering substrate is considered sufficiently stable. The remaining question is no longer *"Can the system execute correctly?"* but:

> Does the current abstraction of durable judgment work across different domains?

This milestone is therefore **an experiment**, not a feature milestone. No new reasoning capability will be added before the experiment is complete.

---

## 2. Research Question

> Can a single durable judgment interface produce meaningful durable knowledge across fundamentally different kinds of information?

Specifically:

- Is the abstraction sufficiently general?
- Are failures primarily model failures or interface failures?
- Does one judgment per update adequately represent real knowledge formation?

The outcome determines whether LYR proceeds directly to verification (M3.1-C) or first revises the Builder abstraction.

---

## 3. Scope

**Includes:** running the existing Builder unchanged; collecting JudgmentRecords; reviewing failures; classifying failure modes; deciding the next architectural step.

**Excludes:** prompt improvements, verifier, challenger, multi-round reasoning, retrieval improvements, cognitive layer, builder redesign. The Builder and prompt remain **frozen** throughout.

---

## 4. Experimental Principle

> **Do not change the Builder while collecting evidence.**

Changing prompts or implementation between runs destroys comparability. The objective is to *evaluate* the current abstraction, not continually improve it. Architectural changes are considered only after all planned experiments complete.

---

## 5. Evaluation Domains

Four independent domains; the Builder must execute **without modification** across all four.

- **Experiment 001 — Memoir:** long-term personal experiences, life lessons, persistent beliefs.
- **Experiment 002 — Meeting Notes:** decisions, action items, organizational memory, project state.
- **Experiment 003 — Financial Report:** persistent business trends, recurring risks, durable financial facts.
- **Experiment 004 — Git History:** engineering decisions, architectural evolution, long-term implementation patterns.

---

## 6. Evaluation Procedure

```text
Semantic Nodes → JudgmentBuilder.update() → JudgmentRecord → Human Review → Failure Classification
```

No prompt or Builder modifications between runs. Every JudgmentRecord is preserved.

---

## 7. Evaluation Dimensions

- **Groundedness** — is every durable claim supported by the provided semantic evidence?
- **Durability** — is the knowledge genuinely worth maintaining (lesson / decision / stable preference / persistent pattern / lasting fact) rather than a transient observation?
- **Scope** — is the claim appropriately qualified, or does it over-generalize beyond the evidence?
- **Evidence Independence** — does the Builder distinguish multiple descriptions of the *same* observation from *independent* observations?
- **Candidate Coverage** — did the Builder overlook other obvious durable candidates? Does one judgment sufficiently represent the input?
- **Operation Correctness** — was the selected operation (ADD / UPDATE / MERGE / NO_OP) appropriate?
- **Audit Quality** — does the JudgmentRecord fully explain what the model proposed, how the Builder interpreted it, what the Engine committed, and why the durable state changed?

---

## 8. Failure Taxonomy

Failures are **classified, not immediately corrected**.

- **F1 — Unsupported Abstraction:** the durable claim exceeds the available evidence.
- **F2 — Over-Generalization:** the durable statement is broader than justified.
- **F3 — Under-Abstraction:** the Builder repeats observations instead of producing durable knowledge.
- **F4 — Incorrect Durability Judgment:** preserves what should be transient, or fails to preserve what should be durable.
- **F5 — Evidence Independence Failure:** multiple descriptions of one event treated as independent evidence.
- **F6 — Incorrect Operation:** wrong maintenance op (ADD instead of UPDATE, UPDATE instead of NO_OP, MERGE instead of UPDATE, …).
- **F7 — Candidate Coverage Failure:** multiple independent durable candidates exist, but only one is produced. *May indicate a Builder-interface limitation rather than model quality.*
- **F8 — Audit Failure:** the committed change may be reasonable, but the JudgmentRecord does not sufficiently explain how the decision occurred.

---

## 9. Decision Criteria

After all experiments complete, failures are reviewed **collectively**. Three outcomes:

- **Outcome A — Builder abstraction is valid.** Most failures are judgment-quality, not architecture. → Proceed to **M3.1-C (Verifier)**.
- **Outcome B — Builder interface is insufficient.** Failures consistently arise because one judgment cannot represent the input (F7-dominant). → Investigate **M3.1-B.2 (Multi-Candidate Durable Builder)** before a verifier.
- **Outcome C — Durability theory is insufficient.** Failures show the definition of durable knowledge is inconsistent across domains (F4-dominant across domains). → Revisit the theoretical definition before adding reasoning stages.

---

## 10. Success Criteria

- all four experiments executed
- every JudgmentRecord preserved
- every run reviewed manually
- failures classified
- architectural conclusions based on the complete experiment, not individual runs
- no Builder modifications during data collection

---

## 11. Exit Criteria

Proceed to M3.1-C only if the Builder abstraction appears stable across domains, major failures are attributable to reasoning quality rather than interface design, no unresolved structural issue requires redesign, and JudgmentRecords provide sufficient evidence for future verification stages. Otherwise, revise the Builder first.

---

## 12. Next Milestone

If validated:

```text
M3.1-C:  Semantic → Builder (Proposer) → Verifier → JudgmentRecord → Engine Commit → Durable
```

If the experiment reveals structural limitations, the next milestone addresses those before any verifier is introduced.

## Appendix — Running the experiment

The evaluation kit lives in [`experiments/evaluation/`](../../experiments/evaluation/)
and does **not** touch the Builder or prompt (§4). Records and reviews land under
`experiments/evaluation/` and **are committed** — unlike the gitignored scratch
`experiments/*/runs/` — because M3.1-E requires every JudgmentRecord preserved as
evidence (§10).

> **Paste note (zsh):** interactive zsh does not treat `#` as a comment, so the
> code blocks below are kept **comment-free** — paste them as-is. (Bash is fine
> either way.)

### 0. One-time setup (a live model is required)

```bash
pip install -e '.[anthropic]'
export ANTHROPIC_API_KEY=...
```

> Without a key the Builder cannot run live. A `--canned <file>` response exists
> only for offline *plumbing* tests of the kit — it is **not** experimental
> evidence and must not be used to populate the experiment.

### 1. Collect + preserve, all four domains (Builder frozen)

```bash
for e in experiment-001-memoir experiment-002-meeting experiment-003-financial-report experiment-004-git-history; do
  python experiments/harness.py "$e" --builder --model claude-opus-4-8
  python experiments/evaluation/evaluate.py review "$e"
done
```

The first line runs the frozen builder (writing to `runs/`); the second preserves
the record and writes a skeleton. Each `review` writes:
- `experiments/evaluation/records/<exp>__<judgment_id>.json` — the preserved record (committed evidence)
- `experiments/evaluation/reviews/<exp>__<judgment_id>.json` — a review skeleton to fill in

### 2. Review each run by hand (design §7 / §8)

Open every `reviews/<exp>__<jid>.json` and fill in:
- `dimensions[*].rating` → `ok` | `weak` | `fail` (the seven dimensions, §7)
- `failures` → any of `F1`..`F8` (§8)
- `reviewer`, `verdict`

The `_context` block (statement, evidence resolved to fixture labels, evidence
groups) is regenerated from the record — **don't edit it**; it's there to review against.

### 3. Summarize and decide (§9)

```bash
python experiments/evaluation/evaluate.py summarize
```

`summarize`:
- tallies failures per domain and overall, and prints the **Outcome A/B/C** decision
  *inputs* (the decision itself is a human call over the complete set — §9, never
  auto-selected);
- **enforces §4**: it flags if the preserved records were not all produced by the
  **same** prompt version / provider / model, since a mid-experiment change would
  destroy comparability.

### Rule

**Do not change the Builder or prompt while collecting evidence (§4).** If a change
seems necessary, that is itself a finding (Outcome B/C): record it, finish the round,
and decide the architectural step afterward.
