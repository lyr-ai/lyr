# LYR M3.1-B Design — Minimal Durable Builder

**Status:** Draft
**Stage:** M3.1-B
**Prerequisite:** [M3.1-A Judgment Contract](./M3.1-A-judgment-contract.md)

---

## 1. Objective

Implement the smallest executable Durable Builder.

The goal is **not** to maximize judgment quality.

The goal is to establish the first end-to-end pipeline that transforms Semantic knowledge into Durable knowledge while recording every judgment through the Judgment Contract.

This milestone is intentionally minimal.

---

## 2. Scope

Input

```text
Semantic Nodes
+
Existing Durable Nodes
```

Output

```text
JudgmentRecord
+
Engine Action
+
Updated Durable Version
```

The builder performs exactly one reasoning step.

---

## 3. Out of Scope

This milestone intentionally excludes:

* Verifier
* Challenger
* Reviser
* Multi-round reasoning
* Confidence estimation
* Cognitive Builder
* Ensemble models
* Optimization

Those belong to later milestones.

---

## 4. Pipeline

```text
Semantic Nodes
        │
        ▼
Candidate Retrieval
        │
        ▼
LLM Durable Builder
        │
        ▼
Structured Judgment
        │
        ▼
Engine Validation
        │
        ▼
JudgmentRecord
        │
        ▼
Durable Commit
```

The builder executes exactly once.

No retries.

No second opinion.

---

## 5. Candidate Retrieval

The builder never reasons over the entire Durable Store.

Instead it receives a bounded candidate set.

Inputs:

* new Semantic Nodes
* matching Durable Nodes

The retrieval strategy may evolve over time.

The builder itself is retrieval-agnostic.

---

## 6. Builder Interface

```python
DurableBuilder.update(
    semantic_nodes,
    candidate_durable_nodes,
) -> JudgmentResult
```

Returns

```python
JudgmentResult(
    judgment_record,
    engine_action,
    updated_durable,
)
```

This becomes the stable interface for all future Durable Builders.

---

## 7. Model Responsibility

The model receives:

* Semantic Nodes
* Candidate Durable Nodes

The model proposes exactly one operation.

Allowed operations:

* ADD
* UPDATE
* MERGE
* NO_OP

The model also explains:

* why this action was selected
* which evidence supports it

The explanation is preserved inside the JudgmentRecord.

---

## 8. Engine Responsibility

The engine never invents knowledge.

The engine only:

* validates references
* validates output schema
* records JudgmentRecord
* commits Durable changes
* assigns versions
* maintains provenance

The engine remains deterministic.

---

## 9. Durable Commit

If validation succeeds:

```text
Structured Judgment
        │
        ▼
Engine Action
        │
        ▼
New Durable Version
```

Every committed version stores exactly one:

```text
judgment_id
```

back-reference.

Rejected and NO_OP judgments create no new Durable version.

---

## 10. Testing Strategy

This milestone is developed using real-world datasets.

The same builder must operate without modification across multiple domains.

Initial evaluation datasets:

* Memoir
* Meeting notes
* Financial reports
* Git history

The objective is not perfect accuracy.

The objective is observing whether the same abstraction works across different knowledge sources.

---

## 11. Development Workflow

Development follows an iterative research loop.

```text
Implement

↓

Run on real data

↓

Inspect JudgmentRecord

↓

Improve Builder

↓

Repeat
```

Theory and implementation evolve together.

No large redesigns should occur before empirical testing.

---

## 12. Success Criteria

M3.1-B is complete when:

* the builder accepts Semantic Nodes and candidate Durable Nodes
* one structured judgment is produced
* a valid JudgmentRecord is persisted
* the engine commits the corresponding Durable update
* the same implementation executes successfully on all evaluation datasets
* no Verifier or Challenger is required

---

## 13. Future Work

M3.1-C introduces verification.

```text
Semantic

↓

Proposer

↓

Verifier

↓

JudgmentRecord

↓

Engine Commit

↓

Durable
```

The Builder interface introduced in M3.1-B remains unchanged.

Verification becomes an additional reasoning stage rather than a redesign of the Durable Builder.
