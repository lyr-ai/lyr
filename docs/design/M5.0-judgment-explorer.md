# LYR M5.0 Design — Judgment Explorer

**Status:** Proposed
**Stage:** M5.0
**Prerequisite:** M3.1 complete

---

## 1. Motivation

LYR now contains a complete model-driven durable knowledge pipeline:

```text
Source → Semantic → Judgment Decomposition → Judgment Builder → Durability Verifier → Durable Knowledge
```

The system is experimentally validated, but the reasoning process remains largely
invisible. Most AI systems expose only the final answer. LYR's primary contribution
is not merely producing durable knowledge — it is preserving **how** that knowledge
was formed. The Judgment Explorer makes that process observable.

---

## 2. Goal

The Explorer is **not** a chat interface and **not** another memory browser. Its
purpose:

> Let a user inspect the complete lifecycle of one durable judgment.

The user should understand what evidence existed, how the Builder interpreted it, how
the Verifier evaluated it, and what the Engine ultimately committed.

---

## 3. Design Principles

- **P1. Show reasoning, not only results.** Not `input → answer` but
  `evidence → semantic → builder proposal → verifier verdict → engine commit → durable`.
  The reasoning process is the product.
- **P2. Every stage is inspectable.** Every transition is expandable; nothing hidden.
- **P3. One judgment at a time.** The Explorer visualizes one `JudgmentRecord`; it
  never summarizes the whole knowledge base.
- **P4. Read-only.** It explains; it never edits knowledge.

---

## 4. User experience

The interface centers on one `JudgmentRecord`, as a vertical lifecycle whose stages
expand independently:

```text
Semantic Evidence → Builder Proposal → Verifier Verdict → Engine Action → Durable Memory
```

---

## 5–9. Panels

- **Evidence** — cited semantic nodes, evidence grouping, duplicate evidence,
  supporting observations. *(What information did the Builder receive?)*
- **Builder** — operation, statement, kind, rationale, confidence, counter-evidence.
  *(What did the Builder think should become durable?)*
- **Verifier** — `KEEP` / `REJECT` / `UNSURE`, rationale, and execution status
  (`SUCCESS` / `ERROR`). *(Should this knowledge persist?)*
- **Engine** — committed operation, version, identity, `judgment_id`, resulting
  durable memory. *(What actually changed?)*
- **Provenance** — recursive `durable → semantic → source` expansion. *(Explain the
  statement back to its original evidence.)*

---

## 10. Example (real records)

**Coffee** — `Semantic: morning coffee ritual` → `Builder: ADD (preference)` →
`Verifier: REJECT ("recurring routine alone is insufficient")` → `Engine: NO_OP`.
No durable memory created.

**Family** — `Semantic: family decisions` → `Builder: ADD ("family consistently
takes priority over career")` → `Verifier: KEEP` → `Engine: Durable v1`.

Both are actual `JudgmentRecord`s from the M3.1-C.1 verified run, not mockups.

---

## 11. Blog integration

The Explorer supports a public demo: readers of the M3.1 article click through
**actual** `JudgmentRecord`s, so the article demonstrates Builder / Verifier / Engine
behavior with real experimental evidence rather than screenshots. This drives the
implementation choice: a **self-contained** page (no build step, no server, no
external requests) that can be opened from disk, embedded in a blog, or served as a
static file — bundling the real records as data.

---

## 12. Non-goals

No chatting, retrieval, editing, memory creation, prompt engineering, or agent
interaction. The purpose is understanding.

---

## 13. Success criteria

A first-time user can inspect a `JudgmentRecord` and answer, without reading code:
what evidence existed; what the Builder proposed; why the Verifier kept or rejected
it; what changed in durable memory; and whether the durable memory traces back to
source.

---

## 14. Future extensions

Later, the Explorer may visualize `Source → Semantic → Durable → Cognitive` — how
multiple durable memories contribute to higher-level cognition (M4+). The initial
Explorer focuses solely on the M3.1 durable-knowledge lifecycle.
