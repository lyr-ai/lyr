# Removing bottlenecks, not adding capability: the LYR M3.1 research arc

*How a memory system learned to form durable knowledge — by treating each
architectural change as an experiment that removes one measured failure mode and
exposes the next.*

---

## The question

LYR models knowledge as layers built over immutable observations: **Source →
Semantic → Durable → Cognitive**, where every layer above Source is the same shape —
a labelled claim that cites its evidence one layer down. The hard, open layer is
**Durable**: *what, out of everything that happened, is worth keeping for the long
term?*

The M3 substrate already answered the trustworthy-mechanics half — identity,
version history, provenance, and an `ADD / UPDATE / MERGE / NO_OP` lifecycle — under
one principle:

> **Model proposes meaning. Engine commits identity, history, and provenance.**

M3.1 asked the other half: *can a model actually make durable-knowledge judgments
well?* The interesting part is **how** we found out. We did not keep making the model
more sophisticated. We repeatedly (a) built the smallest thing that could work,
(b) ran an experiment that could falsify it, and (c) let the dominant failure mode
tell us what to build next.

---

## Stage 1 — one judgment per batch (M3.1-B / B.1)

The minimal durable builder does exactly one thing: take some semantic records,
prompt a model for **one** maintenance operation, and commit it — recording *how* it
decided in an immutable `JudgmentRecord` (the model's proposal verbatim, and the
action the engine actually committed, which may differ when an invariant intervenes).

Before trusting a noisy model policy, the contract was hardened (**B.1**): unique
per-execution ids vs. content fingerprints, frozen/tuple-backed records, raw model
output preserved distinctly from the parsed interpretation, and a corrected,
honest claim about what "replay" does. The point of B.1 was not features — it was
making the audit artifact trustworthy enough that later experiments could be
*believed*.

**Assumption baked in:** one batch of evidence → one durable judgment.

## Stage 2 — the experiment that falsified it (M3.1-E)

We froze the builder and ran it, unchanged, across four deliberately different
domains — a **memoir**, **meeting notes**, a **financial report**, and **git
history** — and classified every failure. The rule was strict: *do not change the
builder while collecting evidence.*

One failure dominated **all four** domains: **F7 — candidate coverage.** Each batch
contained several independent durable candidates, but the one-judgment interface
emitted a single record and silently dropped the rest (the memoir's decades of
weekly letters; the meeting's database-migration reversal; the report's guidance
revision and dividend policy; the repo's auth-fragility pattern).

Crucially, **this was not a model-reasoning failure.** The model produced grounded,
well-scoped judgments and correctly identified duplicate evidence. The limit was the
**interface**, not the model.

This is the first deep result, and it generalizes far beyond LYR:

> **Judgment quality can be *masked* by interface limitations.** With one output per
> batch, you cannot even measure whether the model can judge durability — because
> most of what it would judge never surfaces.

## Stage 3 — decomposition, and the bottleneck it exposed (M3.1-B.2)

The fix was not a smarter model. It was an explicit **judgment-decomposition** stage
*before* the builder: split a batch into one coherent topic per unit, then run the
**unchanged** builder once per unit. One record still equals one decision; the
builder's public interface never changed.

Coverage jumped from **one** durable per batch to **three-to-five**, and the
previously-dropped candidates surfaced. **F7 was solved (4/4 → 0/4 domains).**

But surfacing every candidate exposed what the interface had hidden. Judging each
topic *in isolation*, the model began **over-promoting trivia**: a coffee ritual, a
donut habit, a single-quarter metric — all proposed as durable. A **new** dominant
failure appeared: **F4 — durability judgment.**

The honest framing of what decomposition achieved:

> It did not improve judgment quality. It **isolated** judgment quality from
> interface quality — moving the system from *"which one should I pick?"* to the
> real question, *"should this be durable?"*

## Stage 4 — a benchmark, then a task freeze (durability-v1 / M3.1-C0)

Before building a verifier, two acts of discipline.

First, the F4 evidence was preserved as a **benchmark**: the 19 proposed durable
memories from the decomposed runs, each with a human `deserves_persistence` label
(and honest handling of debatable cases — a provisional label is scored separately,
not force-frozen to look clean). This turns "the verifier is better" from an
assertion into a measurement any future verifier re-runs against.

Second — and this is the subtle one — we froze the **task** before writing a line of
the verifier (**C0**). Left undefined, a "verifier" drifts: reject trivia today,
check grounding tomorrow, scope next, contradiction later, until it is just a second
builder. So four things were fixed in advance: it may only **veto** (never rewrite or
re-operate); it sees only the builder's own judgment context; it answers exactly one
question (*should this persist?* — not truth, usefulness, or style); its output is
`KEEP / REJECT / UNSURE`. Two guards were added: it is **stateless** (one proposal,
no cross-judgment reasoning), and a failed run is a distinct **ERROR**, never a
silent UNSURE — a broken verifier must not masquerade as "maybe keep it."

## Stage 5 — the verifier, and a frozen evaluation (M3.1-C / C.1)

The durability verifier gates at the commit boundary: the builder proposes, the
verifier judges, the engine commits the write or a `NO_OP` — one immutable record
carrying the whole story (proposal → verdict → committed action).

The **scorer and metric were frozen before the run**, so the rules could not be tuned
to the output. Then, once:

**Primary result (frozen `durability-v1`, `gpt-4o`):**

```
KEEP=13  REJECT=4  UNSURE=0   execution errors: 0
false positives = 0     false negatives = 1
```

- **False positives → 0.** Every trivial case was rejected — coffee, donuts,
  single-quarter metric. **On the frozen `durability-v1` benchmark, the observed F4
  over-promotions were eliminated.** (19 cases: enough to demonstrate the failure
  mode and its fix, not to claim F4 is solved in general.)
- **One false negative:** a guidance-reversal (a durable trend expressed as numbers)
  was over-pruned. A precise, narrow failure mode: the verifier cannot yet tell a
  *durable change in direction expressed in numbers* from a *transient single
  metric*.

A separate end-to-end run over all four domains (an ecological-validity check, kept
out of the score) **reproduced** exactly this: no trivia committed, the same single
over-prune, zero errors, complete audit trails.

## The shape of the whole program

```
M3.1-B     one judgment            → F7 dominates      (candidate coverage)
   ↓
M3.1-B.2   decomposition           → F7 solved → F4 dominates  (durability judgment)
   ↓
M3.1-C     durability verifier     → F4 eliminated on durability-v1 (FP→0); one narrow FN remains
```

Read top to bottom, this is not a feature list. It is a sequence in which **each
architectural change eliminated one dominant failure mode and exposed the next.** The
system got better not because the model got bigger, but because each experiment
found the *actual* current bottleneck and removed it.

## What generalizes

1. **Interfaces mask capability.** You cannot measure a model's judgment on candidates
   your interface never surfaces. Fixing the interface is often the prerequisite to
   even *seeing* the real problem.
2. **Freeze the question before the implementation.** A task definition frozen up front
   (C0) is what keeps a component from quietly growing into something else.
3. **Freeze the metric before the results.** The benchmark and scoring rules were fixed
   before the verifier ran, so a good-looking number could not be manufactured after
   the fact.
4. **Classify failures; don't reflexively fix them.** Naming F7, then F4, then a single
   FN — rather than patching each as it appeared — is what made the progression legible.
5. **Separate responsibilities cleanly.** *Builder:* can this be durable? *Verifier:*
   should it? *Engine:* how is it committed? No overlap — which is what let each be
   evaluated on its own.

## Where this leaves the project

The durable layer is now a **stable, model-driven, evaluated substrate** — a real
foundation for the Cognitive layer (M4) rather than a moving target beneath it. The
remaining false negative is a **characterized model behavior**, not an architectural
uncertainty: chasing it now would be optimization, not discovery. The more valuable
next step was to record the program itself — which is this document.
